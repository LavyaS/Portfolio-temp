The problem

Coffee reference material is scattered — origin data on trade sites, tasting notes on retailer pages, brewing steps on separate blogs. There was no single place to go from “where is this from” to “how do I brew it.”

What it is

A single-page atlas: 47 regional coffee profiles across 25 producing countries, filterable by process, altitude and flavour family, with a world map, a variety encyclopedia, a processing lab, a brewing guide, and a quiz that recommends a coffee.

Decisions worth defending

  • Dependency-free by design — markup, styles, data and a hash-based router all live in one index.html, so it deploys anywhere with zero build step.
  • Wrote a small store layer shaped like a REST API even though the data is static, so a real backend could sit behind it later without touching the UI.

Where it fought back

The origins map needed real coastline geometry, not a placeholder grid — reprojecting Natural Earth land data by hand into the app’s own coordinate system took longer than every other feature combined.

Outcome

Live. Every dataset is attributed to a real source (SCA/WCR, ICO, FAOSTAT), and the UI is explicit that sensory scores are editorial estimates, not claims about a specific farm or lot.

The problem

Most physics demos either hard-code stability or skip control entirely. I wanted to watch a controller actually reason about forces — correcting, overcorrecting, damping — instead of just watching things fall.

What it is

A Flask API drives a NumPy-based Newtonian physics engine; a canvas frontend renders it live. Objects can be handed to an AI stabilizer that uses a PID controller plus rule-based overrides to hold them at a target position, with every correction logged and explained.

Decisions worth defending

  • Split the physics engine, the stabilizer and the API into separate modules, so the control logic could be tuned independently of the simulation loop.
  • Logged every AI decision by its proportional / integral / derivative contribution, not just the resulting force — so the stabilization is explainable, not a black box.

Where it fought back

Tuning the PID gains: too aggressive and objects overshoot and oscillate, too soft and they never settle. Got it stable with rule-based overrides on top — emergency damping past a velocity threshold, a push back toward center near boundaries.

Outcome

Working end-to-end — REST API, physics engine and stabilizer, documented with UML diagrams in the repo. Runs locally via Flask; not deployed.

Approach

How I got here and how I work. Short version.

I started with C because I wanted to know what a variable actually is. I'm at MIT-WPU for Computer Engineering, and I default to building over reading — a data structure makes sense to me once I've implemented it, not before.

Most of what I know arrived the same way: something didn't work, and I refused to move on until it did. I read the error, then I read the source. It is slower than copying an answer and it is the only method that has ever compounded.

I care about the parts nobody sees — how the data is shaped, what happens when the input is wrong, whether the thing still works on a slow phone with a bad connection. A feature that only works on the happy path isn't finished, it's demoed.

The engineer I want to become can move from a memory layout to a trained model to a working interface without switching tools of thought. Systems, data and product aren't different careers to me. They're different ends of the same problem.
